ops- reference

The ops- suite works out which of your installed skills fit a problem that needs more than one skill, and in what order. It writes that order up as the full written plan the run executes (the OPORD). It then runs the plan, or monitors you running it. Sequences that keep succeeding go into the library of plans that worked before (the opening book). The methods are adapted from military planning; the rationale is in the README section Why military planning.

ops-recon -> ops-plan -> ops-order -+-> ops-run ----+-> ops-learn
                                    +-> ops-assess -+

ops-assess takes the place of ops-run when you run the plan's skills by hand. ops-learn follows either one.

Install#

Install all six skills:

npx skills add shinytoyrobots/skill-suites --skill ops-recon --skill ops-plan --skill ops-order \
  --skill ops-run --skill ops-assess --skill ops-learn

List what is available, then install any subset:

npx skills add shinytoyrobots/skill-suites --list

ops-plan is useful on its own. The other skills take its output as their input.

Skills#

Every entry uses the same rows. All six skills declare the capability class meta-orchestration.

ops-recon#

Tier IIINever stops
Purpose
Builds an inventory of installed skills (the force roster). It sorts them by what kind of work each skill does (its capability-class) and how heavy a lift each skill is (its tier).
Use when
You ask what skills you have, or want your skill library inventoried or mapped. Also before planning with ops-plan when no fresh inventory (force roster) exists.
Not for
Questions about how a single skill works, or about the agent host's own features.
Arguments
  • none: scan the default roots.
  • a path: scan only that directory (every SKILL.md beneath it). This replaces all default roots, including command files. Skills found get scope: path.
  • manual: you supply the list. It asks for each skill's name, description, and optionally what kind of work it does (its capability-class).
  • --out <dir>: write the roster into that run directory. ops-plan passes this.
Reads

The frontmatter of each skill (name, description, compatibility, metadata) under these roots. It follows symlinks.

ScopeRoots
project./.agents/skills, ./.claude/skills, ./.grok/skills, ./.codex/skills
user~/.agents/skills, ~/.claude/skills, ~/.grok/skills, ~/.codex/skills
command files~/.claude/commands/*.md (top level only)

Duplicates are merged by name. The project copy wins over the user copy; other locations are listed under also-at. A missing root is skipped.

Writes

force-roster.yaml, to the first of:

  • the --out directory;
  • the latest effort directory, if it holds a force-roster.yaml but no situation-assessment.yaml (an unclaimed recon), overwriting that roster;
  • a new ./.ops/{YYYY-MM-DD}-recon/.
Stops for your decision
Never. In manual mode it asks you for the skill list.
Requires
Nothing beyond a host that loads Agent Skills.

III
Typically next
ops-plan

ops-plan#

Tier IStops for you
Purpose
Runs a structured situation check (METT-TC) on a problem. Recommends which installed skills to run, in what order, as a candidate plan (a COA).
Use when
You ask which skills to use for a goal, or want a multi-step effort planned or its options compared before running anything. Also when you say "plan this" about work your skill library could do.
Not for
General project planning, roadmaps, or questions about military doctrine itself.
Arguments
  • a problem statement (required).
  • urgency: immediate | routine | deliberate (optional). When absent, it is inferred: "now", "quick", "urgent", "ASAP" mean immediate. "Strategic", "evaluate options", "high-stakes", "important decision" mean deliberate. Anything else is routine.
UrgencyPlanning budgetWhat runs
immediateunder 5% of contextNo full situation check (METT-TC). Uses a matched chain from the library of plans that worked before (the opening book), else 1–3 roster skills. No stress-testing the plan before running it (wargaming), backup skills, or adaptation rules.
routineabout 15%Full situation check (METT-TC), one candidate plan (a COA), pre-execution gates, and assuming the plan failed and working out why (a pre-mortem).
deliberateabout 25%Full situation check (METT-TC), two or three candidate plans (COAs), full stress-testing (wargaming), your review.
Reads
  • opening-book.yaml: the library of plans that worked before (the opening book), including its known-bad sequences (failure patterns). A missing file is treated as empty.
  • force-roster.yaml: claims an unclaimed recon directory if one is latest. Otherwise copies an inventory (force roster) under 30 minutes old from the latest effort, or runs ops-recon with --out.

The meta-orchestration class is excluded, so a plan never schedules an ops- skill.

Writes

Into a new run directory ./.ops/{YYYY-MM-DD}-{topic-slug}/, or a claimed recon directory renamed to that form:

  • situation-assessment.yaml: all six blocks of the structured situation check (METT-TC).
  • coa-recommended.md: the recommended candidate plan (a COA), with its skill sequence, backup skills, adaptation rules, risk assessment, and notes from stress-testing the plan before running it (wargaming notes).
Stops for your decision
  • When an earlier plan matches closely enough to reuse (confidence above 0.85): reuse it and skip the full situation check (METT-TC), or analyze from scratch.
  • At deliberate urgency: one decision on the comparison of candidate plans (COAs) and the recommendation, before anything is written.
Requires
Nothing beyond a host that loads Agent Skills. With no inventory (force roster) and a failed ops-recon, it plans in degraded mode and says so.
Tier
I
Typically next
ops-order, or run the skills by hand in the order shown.

ops-order#

Tier INever stops
Purpose
Turns the recommended candidate plan (the COA) into the full written plan the run executes (the OPORD). It has five paragraphs: Situation, Mission, Execution, Sustainment, and Command and Signal. It adds per-skill tasking, backup skills, and pre-committed adaptation rules.
Use when
You have a plan from ops-plan and want it made executable, or ask for the full written plan the run executes (an OPORD). Also when you want tasking and contingencies written before running a multi-skill effort.
Not for
General task lists, project plans, or tickets.
Arguments
  • none: use the latest effort directory's coa-recommended.md.
  • a path: a coa-recommended.md file, or a run directory containing one.
Reads
  • coa-recommended.md (required). If none is found it prints "No recommended plan found. Run ops-plan first." and stops.
  • situation-assessment.yaml (optional). If missing, the Situation paragraph is derived from the recommended plan alone, with a note saying so.
  • force-roster.yaml in the same directory, for tiers the assessment lacks.
Writes
opord.md, in the same run directory as the recommended plan. If that plan came from outside ./.ops/, it creates a new run directory and notes the source.
Stops for your decision
Never. It sets the points where the run stops for your decision (HITL checkpoints) that ops-run later acts on.
Requires
Nothing beyond a host that loads Agent Skills.
Tier
I
Typically next
ops-run, or run the tasking table by hand and monitor with ops-assess.

ops-run#

Tier IStops for youNeeds subagents
Purpose
Executes the full written plan (the OPORD) phase by phase, launching each skill as its own subagent. It applies the plan's adaptation rules and stops at your checkpoints. Its state file lets a run pause for days and resume.
Use when
You want the full written plan the run executes (an OPORD) carried out, ask to run or resume the plan, or want to start from a given phase.
Not for
Producing the plan (ops-plan, ops-order), monitoring skills you run by hand (ops-assess), or running a single skill directly.
Arguments
  • none: offer to resume an execution in the latest effort whose status is in-progress, escalated, or paused. Otherwise start that directory's opord.md.
  • a path: an opord.md, or a run directory containing one.
  • --phase N: start or resume at phase N.
  • --dry-run: parse and display what would run. Launches nothing and writes no state.
Reads
  • opord.md (required). If none is found it prints "No OPORD found. Run ops-order first." and stops.
  • situation-assessment.yaml and coa-recommended.md, when present.
  • execution-state.yaml, on resume.
  • force-roster.yaml, refreshed with the ops-recon scan before validation.
Writes
  • execution-state.yaml, after every change.
  • force-roster.yaml, refreshed in the run directory.
  • execution-report.md, on completion or abort.
  • One entry appended to pattern-queue.yaml in the durable-state directory. An aborted run is recorded with output-quality: low.
Stops for your decision
  • After each step the plan flags hitl: true: approve, approve with conditions, or reject. Reject pauses the run.
  • When the plan's frame no longer holds at a phase boundary (an anti-fixation check): continue as planned, or pause and re-run ops-plan.
  • When a condition that stops and asks you instead of guessing (an escalate trigger) matches.
  • When the backup skill also fails (N-2), at every checkpoint level.
  • When it finds resumable state: resume, restart the current phase, or abort.

It also halts, without a choice, on a failed validation or a failed phase transition criterion.

Requires
A host that can launch subagents and pause mid-run for a person's decision. Without both, use ops-assess to monitor a hand-run plan.
Tier
I
Typically next
ops-learn

ops-assess#

Tier IIStops for you
Purpose
Monitors a full written plan (an OPORD) that you run by hand. It runs the observe–orient–decide–act loop (OODA) on each step's output. It applies the plan's adaptation rules and backup skills, and writes the execution report.
Use when
You are running the skills in a full written plan (an OPORD) yourself and want each step checked. Also when you ask to assess or monitor execution, or want a partly-run plan evaluated.
Not for
Code review, QA, general assessments, or automated execution (ops-run).
Arguments
  • none: the latest effort directory's opord.md.
  • a path: an opord.md, or a run directory containing one.
Reads
  • opord.md (required). If none is found it prints "No OPORD found. Run ops-order first." and stops.
  • execution-state.yaml, when present, since ops-run may have executed some phases.
  • Each step's output file, at the path in the plan's tasking table.
Writes
  • execution-report.md. If ops-run already wrote one, it updates that report.
  • One entry appended to pattern-queue.yaml, on a complete run only. It skips this when ops-run already reported the same run.
Stops for your decision
  • When a step has no output yet: check again, skip, or run it now.
  • When a step escalates: continue anyway, re-run this step, abort and re-plan, or give guidance. The question names the trigger that matched, if any.
  • When the backup skill also fails (N-2), at every checkpoint level.
  • When the plan's frame no longer holds at a phase boundary (an anti-fixation check): continue, re-run ops-plan with a new problem statement, or adjust the remaining steps.

A fix it applies on its own without asking (an auto-adapt rule) never interrupts you.

Requires
Nothing beyond a host that loads Agent Skills. You run the plan's skills yourself.
Tier
II
Typically next
ops-learn, or ops-assess again to pick up where a partial run stopped.

ops-learn#

Tier IVNever stops
Purpose
Promotes recurring successful sequences from the candidate new entries waiting on review (the pattern queue) into the library of plans that worked before (the opening book). It records known-bad sequences (failure patterns). It lowers confidence on unused plans: an old plan gets checked harder the longer it has sat unused (confidence decay).
Use when
You ask to update or review the library of plans that worked before (the opening book), or to promote learned patterns. Also after several ops-run or ops-assess executions, to close the learning loop.
Not for
Model training, or general "what did we learn" retrospectives.
Arguments
None.
Reads
pattern-queue.yaml and opening-book.yaml in the durable-state directory. A missing file is first created from the empty template in the skill's own assets/.
Writes
  • opening-book.yaml: new and reinforced plans, known-bad sequences (failure patterns), and decayed confidence.
  • pattern-queue.yaml: trimmed of entries that contributed to a promotion or a failure capture. The rest stay to keep accumulating.

Unknown keys and comments in hand-edited files are preserved.

Stops for your decision
Never.
Requires
Nothing beyond a host that loads Agent Skills.
Tier
IV
Typically next
ops-plan on a new problem, or ops-recon if your skills have changed.

Run directory#

Each effort gets one directory in your project:

./.ops/{YYYY-MM-DD}-{topic-slug}/
FileWritten byContents
force-roster.yamlops-reconThe inventory of installed skills (the force roster), by kind of work (capability class)
situation-assessment.yamlops-planThe six blocks of the structured situation check (METT-TC)
coa-recommended.mdops-planThe recommended candidate plan (a COA)
opord.mdops-orderThe full written plan the run executes (the OPORD)
execution-state.yamlops-runResumable execution state
execution-report.mdops-run or ops-assessExecution log and quality assessment

The latest effort is the run directory whose newest file is most recent. Skills with no path argument use it. A path argument always overrides it.

Output from the skills a plan runs goes to the path in its tasking table. A bare filename goes into the run directory. A skill with no file convention writes step-{phase}-{skill}.md there.

To keep efforts out of version control, add .ops/ to .gitignore.

Durable state#

Two files live outside any project and are shared across all of them:

~/.ops-skills/opening-book.yaml
~/.ops-skills/pattern-queue.yaml
FileWritten byRead by
opening-book.yamlops-learnops-plan, ops-learn
pattern-queue.yamlops-run, ops-assess, ops-learnops-learn
  • When the OPS_STATE environment variable is set, it replaces ~/.ops-skills/ as the directory.
  • A skill that writes a missing file first copies the empty template from its own assets/ directory.
  • A skill that only reads a missing file treats it as empty.

Checkpoint levels (HITL)#

hitl-level sets how often a run has a point where it stops for your decision (a HITL checkpoint). ops-plan sets 2 unless you state a preference. ops-order turns the level into per-step hitl flags; ops-run acts only on those flags.

LevelStops at
0Nothing planned. Only a condition that stops and asks you instead of guessing (an escalate trigger) or a failed backup skill (an N-2 fallback) stops the run.
1Before any terminal deliverable leaves the run directory (published, sent, merged)
2 DefaultLevel 1, plus after every step heavy enough to be tier I or II
3After every step

A condition that stops and asks you instead of guessing (an escalate trigger) stops the run at every level. So does a failed backup skill (an N-2 fallback).

Adaptation rules#

ops-order writes these rules into the plan before it runs. ops-run and ops-assess apply them.

Backup skills#

Every step heavy enough to be tier I or II needs the backup skill to use if the first one fails (an N-1 contingency). It is optional for lighter steps the plan depends on.

n-1-contingencies:
  - skill: "skill-name"
    trigger: "skill unavailable OR output empty after 2 retries"
    substitute-chain: ["alt-skill-1", "alt-skill-2"]
    execution-mode: parallel | sequential
    tradeoff: "description of capability loss"
    n-2-fallback: escalate-to-hitl

When nothing installed can stand in, the entry records substitute-chain: []. That step escalates as soon as it fails.

Rule types#

KeyWhat it isOn match
auto-adapt-rulesA fix it applies on its own without asking (an auto-adapt rule), for predictable failuresRuns the response, records it, and continues
escalate-triggersA condition that stops and asks you instead of guessing (an escalate trigger), for frame-breaking deviationsRuns any automatic actions, then stops for your decision
 
auto-adapt-rules:
  - trigger: "empty output"        # string/pattern match against observed output
    response: "retry with simplified query"
escalate-triggers:
  - trigger: "problem reframed"    # condition description
    response: "surface to the operator — re-run ops-plan"

Each plan needs at least one of each. Escalation order: a fix it applies on its own without asking (an auto-adapt rule) fires silently. A condition that stops and asks you instead of guessing (an escalate trigger) pauses the run. A failed backup skill (N-2) always stops the run, whatever the checkpoint level.

Match mechanism#

Both rule types match by text pattern, never by judgment. The check is mechanical: a substring or pattern present or absent, a pattern count against a threshold, or a file present or absent. The doctrine gives the reason:

"A rule that fires on judgment fires unpredictably, and an operator can't audit why."

Opening book#

The library of plans that worked before (the opening book) stores sequences of kinds of work (capability classes), not skill names. A learned plan survives installing, renaming, or removing skills. ops-plan reads it; ops-learn maintains it.

RuleApplied byValue
Match scoringops-planA trigger phrase appears in the problem: the stored confidence. The problem plainly describes the same workflow: stored confidence + 0.1. No match: 0. A match the problem's task type contradicts counts as no match.
Routing: direct reuseops-planAbove 0.85. Offered to you first; reuse skips the full structured situation check (METT-TC).
Routing: adaptive reuseops-plan0.5–0.85. The stored plan is scaffolding for a new candidate plan (a COA), with light stress-testing (wargaming).
Routing: full analysisops-planBelow 0.5. Treated as no match.
Promotionops-learn3 or more high entries with the same ordered class sequence. A new plan starts at confidence 0.75.
Reinforcementops-learnA known sequence gains 0.02 per new session, capped at 0.95.
Failure captureops-learn2 or more low entries. Recorded as a known-bad sequence (a failure pattern) at confidence 0.60, meaning how sure it is the approach fails.
Decayops-learnLast used more than 30 days ago: minus 0.05, floor 0.30. Plans never used (last-used: null) are exempt.

The routing rows are how sure it is an old plan still fits, and how much re-checking that earns (confidence routing). The decay row means an old plan gets checked harder the longer it has sat unused (confidence decay). At immediate urgency, ops-plan uses a matched chain at any confidence.

Grouping for promotion uses the ordered list of class values only. Tiers are not part of the key. medium entries never promote or fail; they keep accumulating.

Entry schema:

pattern-id: "string"           # kebab-case identifier
triggers:                       # natural language phrases that activate this pattern
  - "compare these options"
capability-chain:               # structural pattern — classes, not skill names
  - class: intelligence-gathering
    tier: II-III
    parallel: true              # can run concurrently with next step
  - class: synthesis-analysis
    tier: II
    depends-on: previous
reference-example:              # one concrete worked example (educational, not prescriptive)
  skills-used: []               # the skill names from the run that produced the entry
  date: null
confidence: 0.75                # 0-1 scale
sessions: 0                     # execution count
last-used: null                 # date of last use

Capability classes#

Each class names what kind of work a step is doing (its capability-class). A skill declares it in metadata.capability-class; otherwise ops-recon infers it from the description or leaves the skill unclassified.

ClassKind of work
intelligence-gatheringScanning, researching, monitoring, detecting signals
synthesis-analysisTurning gathered material into a structured assessment
content-productionWriting, drafting, generating content
content-reviewReviewing, auditing, critiquing, scoring someone's output
planning-designPlans, roadmaps, specs, architectures
execution-orchestrationMulti-step workflows and agent coordination
release-operationsShipping, deploying, announcing, post-release monitoring
retrospective-learningRetros, debriefs, lessons learned
personal-trackingLogging and tracking an individual's own records
market-intelligenceCompetitive intelligence and positioning
financial-legalTax, finance, compliance, contracts
ideation-inventionGenerating novel ideas, exploring concepts
publication-submissionManuscripts, pitches, queries, submissions to outlets
meta-orchestrationAssessing, planning, and dispatching other skills

meta-orchestration is the class every ops- skill declares. ops-plan never schedules it.

Tiers#

Each tier says how heavy a lift a step is (tier I = full multi-agent effort … tier V = a quick check). A skill declares it in metadata.tier; otherwise ops-recon infers it, defaulting to III when signals conflict.

TierScaleCharacteristics
Tier IFull opsMulti-phase, launches 2+ subagents, strongest model, large context, multiple artifacts
Tier IISubstantialStructured workflow, 0–1 subagents, strong model, medium context
Tier IIIStandardSingle-phase, no subagents, one structured output
Tier IVLightweightFast, minimal tooling, read-heavy, feeds higher-tier skills
Tier VAtomicSingle-purpose check/log/status, frequent invocation
